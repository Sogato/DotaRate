# Общие компоненты

> ✅ **Статус документа:** описаны общие пакеты, разделяемые между модулями системы. По мере появления новых общих пакетов они добавляются сюда отдельными разделами.

**Легенда статусов:** ✅ готово и задокументировано · 🚧 в работе · 📋 запланировано

---

## Назначение

Раздел описывает код, который **не принадлежит** ни одному модулю в отдельности, а переиспользуется несколькими. Такой код вынесен в общие пакеты на верхнем уровне репозитория, чтобы у модулей (ML, backend, бот) был единый источник истины для доменных констант и сущностей и не возникало дублирования или рассинхрона.

Ключевое правило зависимостей: **общие пакеты ни от чего не зависят снизу** — они не импортируют код модулей. Зависимость всегда направлена от модуля к общему пакету, не наоборот.

## `dota_core` ✅

Общее доменное ядро системы: конфигурация, справочная БД героев и сущности предметной области Dota 2, нужные более чем одному модулю. Сюда вынесено то, что обязано быть консистентным между обучением и инференсом — в первую очередь маппинг героев и список исключённых героев: если индексы героев разойдутся между модулями, предсказания станут бессмысленными.

```
dota_core/
    config.py
    hero_mapper.py
    data_bases/
        heroes/
            models.py
            create_heroes_db.py
            clear_heroes_db.py
```

### Конфигурация (`config.py`)

Общий конфигурационный модуль системы. Содержит настройки и константы, нужные более чем одному модулю, и является **единой точкой загрузки `.env`**: переменные окружения читаются здесь один раз на всю систему (путь к `.env` — корень репозитория). Локальные config-модули отдельных модулей импортируют этот файл и дополняют его своими константами.

Что лежит в общем config:

- **Базы данных.** Параметры подключения и PostgreSQL-URI: `DATASET_DATABASE_URL`, `HEROES_DATABASE_URL`, `PRO_DATABASE_URL`.
- **Внешние API.** Ключи и эндпоинты Steam API и OpenDota API.
- **Обновляемые параметры патча.** `DOTA_VERSION`, `STARTING_MATCH_SEQUENCE_NUMBER`, `BURST_TIME_TIMESTAMP` — меняются при выходе нового патча Dota 2.
- **Игровые константы Dota 2.** Размер команды (`TEAM_SIZE`), индексы сторон (`RADIANT_INDEX`/`DIRE_INDEX`), битовые маски и количества построек, маски `player_slot`, справочники `GAME_MODES` / `LOBBY_TYPES` / `SERIES_TYPES`.
- **Исключаемые герои.** `EXCLUDED_HERO_IDS` — ID героев, исключаемых из анализа, датасета и обучения. Лежит в общем config именно потому, что используется `HeroMapper`'ом и обязан совпадать на всех стадиях.

> **Двухуровневая схема config.** Каждый модуль имеет свой локальный `config.py`, который первой строкой реэкспортирует общий (`from dota_core.config import *`), а ниже добавляет собственные константы. Благодаря реэкспорту код модуля продолжает импортировать всё из единой точки (`from config import ...`), не различая, общая константа или локальная. Служебные импорты общего config (`os`, `load_dotenv`) скрыты от реэкспорта, поэтому в неймспейс модулей не протекают. Загрузка `.env` происходит разово при импорте общего config — локальные конфиги её не повторяют.

### Справочная БД героев (`data_bases/heroes/`) ✅

Статический справочник героев Dota 2 — общий источник истины об именах и метаданных героев для всей системы. БД вынесена в ядро, потому что её пишет ML-модуль (загрузчиком справочника), а читают все. Держать её в каком-то одном модуле означало бы скрытую зависимость остальных от него.

Пакет содержит SQLAlchemy-модель со своим `declarative_base()` и скрипты применения/очистки схемы.

**Модель `Hero`.** Справочник героев: `id`, системное имя `name`, отображаемое `localized_name`, основной атрибут `primary_attr` (`agi`/`str`/`int`/`all`), тип атаки `attack_type` (`Melee`/`Ranged`), роли `roles` (через запятую).

**Скрипты.**

- `create_heroes_db.py` — применяет схему через `Base.metadata.create_all()`. Существующие данные не удаляются, существующие таблицы не изменяются. Саму базу в PostgreSQL скрипт не создаёт.
- `clear_heroes_db.py` — очищает таблицу через `TRUNCATE ... RESTART IDENTITY CASCADE` (структура сохраняется, счётчик сбрасывается). Операция необратима и транзакционна.

Наполнение БД данными — задача сбора, она остаётся в ML-модуле (`data_collection/heroes_data_loader.py`, см. [`ml.md`](ml.md)).

### `hero_mapper.py` ✅

Класс `HeroMapper` решает проблему **разреженной нумерации** `hero_id` (1, 2, 3, 5, 7, … 145) — для embedding-слоёв нейросети нужны плотные индексы без пропусков (0, 1, 2, …).

- Строит двусторонний маппинг `hero_id ↔ плотный индекс`, читая все ID из БД `heroes`.
- Поддерживает исключение нежелательных героев через `excluded_hero_ids` (передаётся `EXCLUDED_HERO_IDS`).
- Маппинги строятся **лениво** при первом обращении к свойствам и кешируются.
- Свойства: `hero_to_index`, `index_to_hero`, `total_heroes` (размерность пространства героев для embedding). Метод `get_mapping_info()` отдаёт статистику маппинга, `cleanup()` освобождает соединение с БД.

Применяется везде, где `hero_id` нужно подать в модель: в препроцессоре и загрузчике данных ML-модуля, а также при инференсе в backend. **Важно:** исключения героев должны быть консистентны между препроцессингом и обучением/инференсом — маппер строится от одного и того же `EXCLUDED_HERO_IDS` (из общего config), поэтому индексы совпадают на всех стадиях.
