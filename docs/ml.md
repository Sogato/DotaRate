## Назначение

ML-модуль — самостоятельная единица системы Dota Rate, отвечающая за **формирование датасета и обучение моделей**. Модуль не зависит от backend и Telegram-бота: на выходе он производит обученные модели как артефакты, копии которых впоследствии переносятся в backend для инференса в реальном времени. На этом жизненный цикл модуля заканчивается.

Внутри модуль реализует линейный пайплайн: сбор сырых данных из внешних API → хранение в PostgreSQL → валидация → предобработка в ML-формат → обучение и тестирование моделей.

### Роль двух баз матчей

В модуле две базы матчей с разным назначением:

- **`dataset`** (обычные публичные матчи, миллионы записей) — обучающий датасет. Преобразуется в HDF5 и идёт на обучение моделей.
- **`pro`** (профессиональные матчи) — выступает как тестовый набор: тестеры моделей умеют брать данные прямо из неё, чтобы оценить модели на реальных проф. матчах. Также проверяется валидатором.

Модели обучаются на паб-матчах, а оцениваются и на отложенной публичной-выборке (HDF5 test), и на профессиональных матчах из БД `pro`.

# Быстрый старт

Минимум, необходимый, чтобы поднять модуль и пройти пайплайн. Подробные пояснения по каждой стадии в разделе [Подробная документация](#подробная-документация) ниже.

## Требования

- **Python** с зависимостями из `requirements.txt`
- **PostgreSQL** хранилище для всех баз данных
- **Файл `.env`** в корне проекта (на уровень выше `ml_module`):

```
DB_USER=...
DB_PASSWORD=...
DB_HOST=...
DB_PORT=...
DATASET_DB_NAME=...
HEROES_DB_NAME=...
PRO_DB_NAME=...
STEAM_API_KEY=...
```

> **Нюанс импортов.** Скрипты создания/очистки баз импортируют свои модели локально (`from models import ...`), а `config` и `utils` — от корня `ml_module`. Коллекторы и остальные модули используют полные пакетные пути. Для корректной работы корень `ml_module` должен быть доступен в `PYTHONPATH`.

## Порядок настройки

Все стадии на текущем этапе выполняются **вручную и по очереди** — каждая опирается на результат предыдущей.

| № | Действие | Что запустить |
|---|----------|---------------|
| 0 | Создать три пустые базы в PostgreSQL с именами из `.env` (`dataset`, `heroes`, `pro_matches`) | — |
| 1 | Применить схемы (создать таблицы) | `data_bases/heroes/create_heroes_db.py`, `data_bases/dataset/create_dataset_db.py`, `data_bases/pro_matches/create_pro_db.py` |
| 2 | Заполнить справочник героев | `data_collection/heroes_data_loader.py` |
| 3 | Собрать матчи (самая долгая стадия) | `data_collection/data_collector.py`, `data_collection/data_collector_pro.py` |
| 4 | Провалидировать собранные данные | `data_validation/data_validator.py` (интерактивное меню) |
| 5 | Подготовить датасет в HDF5 | `data_processing/hdf5_preprocessor.py` |
| 6 | Обучить модели | `ml_training/model_trainer_win_v1.py`, `model_trainer_score_v1.py`, `model_trainer_time_v1.py` |
| 7 | Протестировать модели | `ml_testing/model_tester_win_v1.py`, `model_tester_score_v1.py`, `model_tester_time_v1.py` |

> **Обязательные зависимости порядка:**
> - таблицы (шаг 1) создаются только в **уже существующих** базах PostgreSQL — сами базы создаются на шаге 0;
> - справочник героев (шаг 2) заполняется **до** шагов 3–7: коллекторы, валидатор, препроцессор, тренеры и тестеры читают данные о героях из БД `heroes` (через `HeroCache` / `HeroMapper`) и не работают, если она пуста.

# Подробная документация

## Конфигурация (`config.py`)

Единый конфигурационный файл, загружающий переменные окружения из `.env`. Сгруппирован по смысловым блокам.

### Подключения и источники данных

- **Базы данных.** Из переменных окружения собираются три PostgreSQL-URI: `DATASET_DATABASE_URL`, `HEROES_DATABASE_URL`, `PRO_DATABASE_URL`.
- **Внешние API.**
  - *Steam API* — `GetMatchHistoryBySequenceNum` (источник обычных публичных матчей для БД `dataset`).
  - *OpenDota API* — эндпоинты героев (`/heroes`), списка проф. матчей (`/proMatches`) и деталей матча (`/matches/{id}`).

### ⚠️ Обновляемые параметры

Эти значения меняются при выходе нового патча Dota 2 и определяют, какие матчи собираются:

| Параметр | Назначение |
|----------|------------|
| `DOTA_VERSION` | Версия патча (напр. `"741d"`), используется в именах файлов и моделей |
| `STARTING_MATCH_SEQUENCE_NUMBER` | Стартовый sequence number для сбора через Steam API |
| `BURST_TIME_TIMESTAMP` | Unix-время выхода патча; матчи старше этой границы отбрасываются |

### Игровые константы

Базовые величины игры: размер команды (`TEAM_SIZE = 5`), индексы сторон (`RADIANT_INDEX`, `DIRE_INDEX`), битовые маски и количества построек (башни, казармы), маски для разбора `player_slot`. Здесь же — справочники-словари `GAME_MODES`, `LOBBY_TYPES`, `SERIES_TYPES`, используемые для валидации и отображения.

### Параметры фильтрации матчей

- `REQUIRED_MATCH_FIELDS` / `REQUIRED_PLAYER_FIELDS` — наборы обязательных полей, без которых матч/игрок отбрасывается.
- `ALLOWED_GAME_MODES` / `ALLOWED_LOBBY_TYPES` — белые списки режимов и типов лобби.
- `VALID_LEAVER_STATUSES` — допустимые статусы выхода игрока (по умолчанию только нормальное завершение и краткий переподключаемый дисконнект).
- `MINIMUM_MATCH_DURATION` — минимальная длительность (1200 с = 20 мин).
- `EXCLUDED_HERO_IDS` — герои, исключаемые из анализа (например, недавно добавленные).

### Параметры определения ролей и руинеров

Эти структуры управляют эвристиками, применяемыми при сборе:

- `SUPPORT_ITEM_IDS` — предметы, повышающие «саппортовость» игрока.
- `HERO_ITEM_EXCEPTIONS` — предметы, которые для конкретных героев не считаются саппортовскими.
- `HERO_SUPPORT_SCORE_EXCEPTIONS` — герои/аспекты, получающие бонус к support-оценке.
- `ROLE_MAPPING` — числовое кодирование ролей для моделей (`core → 0`, `support → 1`).
- `HERO_RUINER_EXCEPTIONS` — компоненты индекса руинера, игнорируемые для героев с нестандартной механикой.

## Утилиты (`utils/`)

Вспомогательные модули, используемые на всех стадиях пайплайна.

### `console.py` ✅

Форматированный вывод в терминал на ANSI escape-кодах. Предоставляет класс `Colors` (палитра цветов, стили, тематические градиенты) и набор функций отображения:

- `print_section_header()` — заголовок главной секции в двойной рамке;
- `print_subsection_header()` — заголовок подсекции с подчёркиванием;
- `print_info_line()` — строка «метка: значение» с иконкой;
- `print_progress_bar()` — прогресс-бар с процентами и счётчиками;
- `print_status_message()` — статусное сообщение с цветовой кодировкой (`success` / `error` / `warning` / `info`).

Это чисто презентационный слой — на данные и логику он не влияет.

### `hero_cache.py` ✅

Класс `HeroCache` — кэш справочных имён героев для быстрого O(1)-доступа.

- Данные загружаются **только** при явном вызове `initialize()`, который читает все записи из БД `heroes` и строит in-memory словарь `{hero_id: localized_name}`.
- Повторные вызовы `initialize()` безопасны (загрузка не дублируется).
- `get_hero_name(hero_id)` никогда не падает: для неизвестных ID возвращает строку-заглушку `"Unknown Hero (ID: X)"`.

Используется коллекторами и валидатором для читаемого логирования. Поскольку БД героев статична во время работы, кэш служит единственным источником истины для имён.

### `hero_mapper.py` ✅

Класс `HeroMapper` решает проблему **разреженной нумерации** `hero_id` (1, 2, 3, 5, 7, … 145) — для embedding-слоёв нейросети нужны плотные индексы без пропусков (0, 1, 2, …).

- Строит двусторонний маппинг `hero_id ↔ плотный индекс`, читая все ID из БД `heroes`.
- Поддерживает исключение нежелательных героев через `excluded_hero_ids` (передаётся `EXCLUDED_HERO_IDS`).
- Маппинги строятся **лениво** при первом обращении к свойствам и кешируются.
- Свойства: `hero_to_index`, `index_to_hero`, `total_heroes` (размерность пространства героев для embedding). Метод `get_mapping_info()` отдаёт статистику маппинга, `cleanup()` освобождает соединение с БД.

Применяется в препроцессоре и загрузчике данных, где `hero_id` нужно подать в модель. **Важно:** исключения героев должны быть консистентны между препроцессингом и обучением/тестированием — маппер строится от одного и того же `EXCLUDED_HERO_IDS`, поэтому индексы совпадают на всех стадиях.

### `time_utils.py` ✅

Небольшая утилита форматирования. Функция `format_timestamp(timestamp, fmt)` переводит Unix-timestamp в читаемую строку даты/времени (формат по умолчанию `YYYY-MM-DD HH:MM:SS`); при некорректном значении возвращает строку-заглушку вместо исключения.

## Стадия 1. Базы данных (`data_bases/`)

Модуль хранения. Содержит три независимых пакета — по одному на каждую базу. У каждого пакета свои SQLAlchemy-модели (`models.py`) с **собственным** `declarative_base()`, а также скрипты создания и очистки.

| Пакет | База | Таблицы | Назначение |
|-------|------|---------|------------|
| `dataset/` | `dataset` | `matches`, `match_players` | Большой корпус обычных матчей для обучения |
| `heroes/` | `heroes` | `heroes` | Статический справочник героев |
| `pro_matches/` | `pro_matches` | `pro_matches`, `pro_match_players` | Профессиональные турнирные матчи |

### Схемы данных

**`heroes` → модель `Hero`.** Справочник: `id`, системное имя `name`, отображаемое `localized_name`, основной атрибут `primary_attr` (`agi`/`str`/`int`/`all`), тип атаки `attack_type` (`Melee`/`Ranged`), роли `roles` (через запятую).

**`dataset` → `Match` + `MatchPlayer`.** Один матч связан ровно с 10 игроками (один-ко-многим, каскадное удаление). `Match` хранит результат, длительность, время, битовые маски построек, тип лобби и режим, счёт команд. `MatchPlayer` — детальная статистика игрока: герой и его вариант, назначенная роль (`core`/`support`, Enum на уровне БД), предметы (6 основных слотов + 3 рюкзака + 2 нейтральных), боевая статистика (`kills`/`deaths`/`assists`/`kda`), экономика (`last_hits`, `denies`, `gold_per_min`, `xp_per_min`, `level`, `net_worth`) и наличие ключевых улучшений (Aghanim's Scepter/Shard, Moonshard).

**`pro_matches` → `ProMatch` + `ProMatchPlayer`.** Структура `ProMatchPlayer` идентична `MatchPlayer`. `ProMatch` дополнительно содержит контекст профессионального матча: ID и названия команд, ID и название турнира (`leagueid` / `league_name`), информацию о серии (`series_id`, `series_type`). Поля команд/турнира допускают `NULL`.

### Скрипты

- **`create_*_db.py`** — применяют схему через `Base.metadata.create_all()`. Существующие данные **не** удаляются; уже существующие таблицы не изменяются. Скрипт **не** создаёт саму базу в PostgreSQL.
- **`clear_*_db.py`** — полностью очищают таблицы через `TRUNCATE ... RESTART IDENTITY CASCADE` (структура схемы сохраняется, счётчики сбрасываются). Операция необратима и транзакционна. Дочерние таблицы (`*_players`) очищаются раньше родительских из-за внешних ключей.

## Стадия 2. Справочник героев (`data_collection/heroes_data_loader.py`) ✅

Заполняет БД `heroes` актуальными данными из OpenDota (`/api/heroes`). Стратегия — **полная замена** (`clear → insert`):

1. Запрос данных из API (таймаут 30 с, аккуратная обработка сетевых ошибок).
2. Очистка таблицы `heroes`.
3. Валидация каждого героя (`validate_hero_data`): наличие обязательных полей и допустимость значений `primary_attr` и `attack_type`. Роли-список конвертируются в строку через запятую.
4. Пакетная вставка валидных записей.
5. Вывод сводной статистики (распределение по атрибутам, типам атаки и ролям).

Эту стадию необходимо выполнить **до** сбора матчей — иначе `HeroCache` не инициализируется и коллекторы остановятся.

## Стадия 3. Сбор матчей (`data_collection/`) ✅

Самая длительная стадия пайплайна. Реализована двумя независимыми коллекторами, каждый со своим источником, своей целевой БД и своей логикой сбора.

| Коллектор | Источник | Целевая БД | Направление сбора | Детекция руинеров |
|-----------|----------|------------|-------------------|-------------------|
| `data_collector.py` | Steam API | `dataset` | от старых к новым | да |
| `data_collector_pro.py` | OpenDota API | `pro_matches` | от новых к старым | нет |

### Общие механики обеих стадий

Оба коллектора инициализируют `HeroCache`, анализируют состояние целевой БД и пропускают каждый матч через **двухступенчатую фильтрацию**.

**Первичная фильтрация** — базовые критерии: время начала (после `BURST_TIME_TIMESTAMP`), допустимые режим/тип лобби (для pub) или тип серии и наличие названий команд (для pro), минимальная длительность, наличие обязательных полей, корректный состав 5×5.

**Вторичная фильтрация** — содержательный анализ:

- *Фильтр ливеров* — отбрасываются матчи с недопустимыми `leaver_status`.
- *Детекция «мёртвых» матчей* (`is_dead_match`) — матчи, где игроки массово вышли в начале (много игроков на 1 уровне, нулевые `last_hits`, низкий суммарный фарм). Такие игры иногда не помечаются Valve как abandoned, но бесполезны для обучения.
- *Назначение ролей* (`assign_player_roles`) — см. ниже.

**Алгоритм назначения ролей.** Для каждого игрока считается `support_score` — взвешенная сумма факторов: количество саппорт-предметов и **инвертированные** экономические показатели (чем ниже `net_worth`/`last_hits`/`GPM`/`XPM` относительно максимума команды, тем «саппортовее» игрок). Учитываются исключения предметов и бонусы для отдельных героев. Игроки сортируются по убыванию `support_score`: двое верхних получают роль `support`, остальные трое — `core`. Несоответствие пропорции 3/2 считается ошибкой и матч отбрасывается.

### Особенности `data_collector.py` (обычные матчи → `dataset`)

Собирает публичные матчи через Steam API инкрементально по `match_seq_num` (от старых к новым). Помимо общих стадий, применяет **детекцию руинеров** (`detect_ruiner_player`): вычисляет `ruiner_index` как взвешенную сумму компонентов — доля смертей от командных (team death ratio), отклонение KDA от ожидаемого для роли, экономическая эффективность (income score) и вклад в убийства (contribution score). Дополнительно матч сразу помечается как руинерский при критических аномалиях в предметах (слишком много пустых слотов или дубликатов). Веса компонентов и пороги настраиваются константами в начале файла; набор `HERO_RUINER_EXCEPTIONS` позволяет отключать отдельные компоненты для специфичных героев. Матч с хотя бы одним руинером отбрасывается.

Сохранение — **чанками** (`DATABASE_SAVE_CHUNK_SIZE`) для производительности при больших объёмах. Сбор останавливается при достижении целевого количества (`TARGET_MATCHES_COUNT`) или когда API несколько раз подряд возвращает заметно меньше матчей, чем запрошено (признак, что достигнут актуальный момент). Поддерживает дозаполнение уже частично собранной БД.

### Особенности `data_collector_pro.py` (проф. матчи → `pro_matches`)

Двухэтапный сбор через OpenDota:

- **Этап 1 — сбор списка.** Постраничный обход `/proMatches` (пагинация через `less_than_match_id`, от новых к старым) с первичной фильтрацией; результат — список ID матчей.
- **Этап 2 — детальная обработка.** Для каждого матча запрашиваются полные данные через `/matches/{id}`, применяется вторичная фильтрация, формируется запись для БД.

Детекция руинеров здесь **не применяется** (для проф. матчей не имеет смысла). Сохранение — единовременное, после полной обработки. Реализована корректная обработка rate-limit (429): при блокировке цикл прерывается, а уже собранные матчи сохраняются.

Коллектор автоматически выбирает один из четырёх **сценариев** в зависимости от состояния БД и временной границы `BURST_TIME`:

| Сценарий | Условие | Задача |
|----------|---------|--------|
| `INITIAL` | БД пуста | Первичное заполнение от новейших матчей до `BURST_TIME` / цели |
| `UPDATE` | БД достигла `BURST_TIME` | Добавление новых матчей сверху (остановка на первом существующем) |
| `BACKFILL` | БД не достигла `BURST_TIME` | Заполнение пробелов до временной границы с проверкой дубликатов |
| `COMPLETE` | Цель достигнута | Сбор не требуется |

## Стадия 4. Валидация данных (`data_validation/`) ✅

Проверка качества и анализ статистики уже собранных данных. Запускается перед препроцессингом, чтобы убедиться в целостности БД.

### Координатор `data_validator.py`

Класс `DataValidator` сам анализ не выполняет — он **главный координатор**: подключается к выбранной БД, инициализирует кэш героев и в правильном порядке запускает компоненты из `data_validation/components/`, собирая итоговый отчёт. Поддерживает два типа баз (`dataset` и `pro`), выбирая конфигурацию через `DatabaseConfig`. Часть проверок выполняется только для `pro`.

Порядок работы: инициализация → информация о размере БД → проверки целостности → анализ матчей (+ проф. статистика для `pro`) → анализ игроков и героев → итоговый отчёт → закрытие сессии. Итоговый отчёт включает объём данных (матчи, игроки, уникальные игроки, герои), баланс сторон (винрейты Radiant/Dire, средняя длительность, временной охват), производительность анализа и список найденных проблем целостности; для `pro` дополнительно — число уникальных команд, лиг и серий.

### Компоненты (`components/`)

Координатор делегирует работу набору анализаторов; их назначение отражено в именах:

| Компонент | Роль |
|-----------|------|
| `DatabaseConfig` | Конфигурация активной БД (модели, URL, флаги поддержки `teams`/`leagues`/`series`) |
| `DatabaseAnalyzer` | Размер и содержимое БД; возвращает счётчики матчей и игроков |
| `IntegrityChecker` | Проверки целостности; возвращает список найденных проблем |
| `MatchAnalyzer` | Базовый анализ матчей (всегда) |
| `ProAnalyzer` | Проф. статистика — команды, лиги, серии (только для `pro`) |
| `PlayerAnalyzer` | Анализ игроков (всегда) |
| `HeroAnalyzer` | Анализ героев (если есть записи игроков; использует кэш героев) |
| `IntersectionChecker` | Быстрая проверка пересечений между двумя базами |

### Запуск

`data_validator.py` запускается с интерактивным меню выбора режима: анализ публичной БД (`dataset`), анализ профессиональной БД (`pro`), быстрая проверка пересечений между базами, либо выход. Для полной проверки обеих баз модуль запускают дважды, выбирая нужный режим.

## Стадия 5. Препроцессинг (`data_processing/hdf5_preprocessor.py`) ✅

Превращает данные из БД `dataset` в оптимизированный формат HDF5 для обучения. Класс `HDF5Preprocessor` создаёт **два независимых файла** в каталоге `datasets/`: основной (`..._main.h5`) для обучения и тестовый (`..._test.h5`) для оценки.

### Что происходит

1. **Отбор матчей.** SQL-запрос получает ID всех валидных матчей (исключая матчи с героями из `EXCLUDED_HERO_IDS`). При заданном `MAX_TOTAL_MATCHES` берётся воспроизводимая случайная подвыборка.
2. **Разбиение train/test.** `TEST_DATASET_SIZE` матчей случайно выделяются в тестовую выборку, остальные — в основную. Разбиение фиксируется сидом `RANDOM_SEED`, поэтому при неизменном наборе матчей воспроизводится.
3. **Потоковая загрузка чанками** (`CHUNK_SIZE`) с агрегацией данных игроков по командам на уровне SQL.
4. **Преобразование** `hero_id` → плотные индексы через `HeroMapper`; строковые роли → числа через `ROLE_MAPPING`; булев результат → 0/1.
5. **Пакетная запись** в HDF5 и **валидация** созданных файлов (баланс классов, диапазон индексов героев, уникальность 10 героев в матче, примеры записей).

### Структура HDF5

Скалярные поля формы `(N,)`: `match_id`, `radiant_win`, `duration`, `radiant_score`, `dire_score`, статусы построек (`tower_status_*`, `barracks_status_*`). Векторные поля формы `(N, TEAM_SIZE)`: составы (`radiant_heroes`, `dire_heroes` — плотные индексы), варианты героев (`radiant/dire_hero_variants`), роли (`radiant/dire_roles`). Все данные — `int64`.

> **Ключевая деталь выравнивания.** Все шесть командных агрегатов (герои/варианты/роли) упорядочены в SQL по `hero_id` через `aggregate_order_by` с одним и тем же ключом. Это гарантирует, что i-е элементы heroes/variants/roles внутри команды относятся к одному игроку, а порядок строк воспроизводим между прогонами. Семантика драфт-порядка (`player_slot`) при этом **не сохраняется** — если она понадобится, её нужно писать отдельным датасетом.

> **Архив.** `data_processing/tfrecord_preprocessor.py` устарел, хранится как архив и в документации не описывается.

## Стадия 6. Обучение моделей (`ml_training/`) ✅

Три типа моделей решают разные задачи по одним и тем же признакам — составам команд. Все три обучаются ансамблем из `N_FOLDS` моделей (K-fold кросс-валидация) на основном HDF5-файле.

### Загрузчик данных (`data_loader_v1.py`)

`DataLoaderV1` приводит данные из трёх взаимозаменяемых источников к единому формату признаков `{'radiant_heroes', 'dire_heroes'}` (плотные индексы, `(N, 5)`):

- **HDF5-файл** — индексы и целевые поля читаются напрямую;
- **БД `pro`** — матчи (с опциональным фильтром по лигам и лимитом) + батчевая загрузка игроков, валидация состава, `hero_id` → индексы; невалидные матчи пропускаются со счётчиком;
- **одиночный матч** — `hero_id` → индексы, без меток (для инференса).

Тип целевой переменной задаётся параметром `target`, а набор читаемых как метки полей — словарём `TARGET_FIELDS`:

| `target` | Поля метки | Форма | Задача |
|----------|-----------|-------|--------|
| `win` | `radiant_win` | `(N,)` | бинарная классификация |
| `score` | `radiant_score`, `dire_score` | `(N, 2)` | регрессия (2 выхода) |
| `time` | `duration` | `(N,)` | регрессия |

Порядок героев внутри команды не сортируется: модель агрегирует состав permutation-invariant pooling'ом, поэтому порядок на результат не влияет.

### Общая архитектура («bag-of-heroes»)

Все три модели делят одну схему: входы (5 Radiant + 5 Dire индексов) → **общий** Embedding-слой с L2-регуляризацией → `GlobalAveragePooling1D` по каждой команде → конкатенация → MLP (`Dense → BatchNorm → ReLU → Dropout`, повторяется по `hidden_units`) → выходной слой. Различаются только голова и функция потерь.

Подход сознательно простой и служит отправной точкой: модель оценивает исход только по «силе» состава, **без** явного моделирования синергий, контр-пиков, позиций или порядка пика. Общий embedding делает представление героя одинаковым независимо от стороны.

### Различия по типам

| | Win | Score | Time |
|---|-----|-------|------|
| Выходной слой | `Dense(1, sigmoid)` | `Dense(2, linear)` | `Dense(1, linear)` |
| Loss | binary crossentropy | MSE | MSE |
| Метрики | accuracy, AUC, precision, recall | MAE, RMSE | MAE, RMSE |
| Кросс-валидация | `StratifiedKFold` | `KFold` | `KFold` |
| Нормализация цели | нет | да (общий mean/std по обоим счётам) | да (mean/std по duration) |

Регрессионные модели (`score`, `time`) обучаются в **стандартизованном** пространстве цели; параметры нормализации (`mean`/`std`) сохраняются в `target_norm.json` рядом с моделями — тестер использует их, чтобы развернуть предсказания обратно в убийства/секунды. Общие гиперпараметры: `RANDOM_SEED=42`, embedding 32, `hidden_units=[256, 128]`, dropout 0.2, L2 0.001, до 1000 эпох, батч 512, LR 0.0005, 5 фолдов. Контроль обучения — `EarlyStopping` (с восстановлением лучших весов) и `ReduceLROnPlateau`.

### Структура хранения и контракт для backend

Каждый запуск обучения создаёт отдельную папку прогона с автоинкрементным номером:

```
models / <DOTA_VERSION> / <MODEL_TYPE> / <MODEL_VERSION> / run_<NNN> /
    model_<type>_v1_<version>_fold_1.keras
    ...
    model_<type>_v1_<version>_fold_5.keras
    target_norm.json          # только для score и time
```

Нумерация `run_<NNN>` устойчива к ручным меткам (`run_001_best` считается занятым номером 1). **Это и есть артефакт, который заберёт backend:** ансамбль из 5 `.keras`-файлов фолдов плюс `target_norm.json` для регрессионных моделей. Контракт инференса: подать признаки `{'radiant_heroes', 'dire_heroes'}` (плотные индексы через `HeroMapper` с тем же `EXCLUDED_HERO_IDS`), усреднить предсказания фолдов (soft-voting), а для `score`/`time` развернуть результат через сохранённые `mean`/`std`.

## Стадия 7. Тестирование моделей (`ml_testing/`) ✅

Три тестера оценивают соответствующие ансамбли. Все интерактивны: запрашивают, какой прогон (`run_<NNN>`) тестировать и на каком источнике данных — **HDF5 тестовая выборка** (отложенные паб-матчи) или **БД `pro`** (профессиональные матчи). Источники взаимозаменяемы — доступ к ним инкапсулирован в `DataLoaderV1`.

### Общий сценарий

1. Адаптивное обнаружение моделей ансамбля (скан папки прогона по шаблону `*_fold_*.keras`).
2. Для `score`/`time` — загрузка `target_norm.json` (без него развернуть предсказания нельзя).
3. Загрузка данных выбранного источника в единый формат.
4. Предсказание каждой моделью по отдельности, усреднение в ансамбль (**soft-voting**); для регрессии — разворот в исходные единицы.
5. Расчёт метрик ансамбля, метрик каждой модели (разброс = стабильность фолдов) и сравнение с baseline.

Baseline считается из истинных меток тестовой выборки и задаёт планку «без модели»: для классификации — мажоритарный класс, для регрессии — предсказание среднего.

### Различия по типам

| | Win | Score | Time |
|---|-----|-------|------|
| Основные метрики | accuracy, precision, recall, F1, AUC | MAE, RMSE, R² (по Radiant, Dire и суммарно) | MAE, RMSE, R², медиана, bias, доля в ±5/±10 мин |
| Доп. разрез | точность по порогам уверенности (0.5–0.7) + матрица ошибок | сводка по командам | ошибка по диапазонам длительности (бакеты 30/40/50 мин) |
| Baseline | мажоритарный класс | предсказание среднего счёта | предсказание средней длительности |

Анализ по порогам уверенности у `win`-тестера соответствует категориям из README (>50% … >70%): для каждого порога считается доля попавших в «уверенную» группу предсказаний и их точность — для хорошо откалиброванной модели точность растёт вместе с порогом.
